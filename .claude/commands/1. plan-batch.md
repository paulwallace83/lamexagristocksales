# /plan-batch — Research, Plan, and Scope a Batch

## Description
Run at the start of every batch. This skill researches the batch, creates an implementation plan, and formalises requirements.

## Instructions

### Step 1: Research
Read these files in order:
1. `CLAUDE.md`
2. `LESSONS.md`
3. The batch document (e.g., `docs/batches/B001-sync-data-quality.md`)
4. All files referenced in the batch document's "Files to Touch" section
5. Any `agent_docs/` files relevant to the batch domain (see CLAUDE.md "Agent Docs" table)
6. `docs/Architecture.md` (if the batch touches data flow, storage, auth, or integrations)
7. All dependency batch documents listed in the batch's "Depends On" section
8. Every file listed in the batch document's "Files to Read (Context)" section
9. Every file listed in "Files to Create/Modify" that already exists in the codebase
10. Any files in `/docs/reviews/` — past code review findings (if directory exists)

Then check for deferred items from prior batches:
- Read all `docs/reviews/batch-*-deferred.md` files that exist
- Skip any items with status `RESOLVED`
- For each OPEN deferred item, flag it as a candidate for this batch if either:
  1. The item's **target batch** matches the current batch ID
  2. The current batch's "Files to Create/Modify" list **overlaps** with the file referenced by the deferred item
- Collect any candidates into a "Deferred items to consider" list for the report below

Then report:
1. What do you understand the task to be?
2. What files will you need to create or modify?
3. What dependencies or packages will you need to install (if any)?
4. **Deferred items to consider** — any deferred items from prior batches that matched by target batch or file overlap. For each, state which deferred file it comes from, which rule matched (target or file overlap), and the original finding. If none match, state "No prior deferred items apply to this batch."
5. Are there any ambiguities or questions?
6. What assumptions are you making?
7. Does anything in the batch document contradict `CLAUDE.md`, `Architecture.md`, or `LESSONS.md`?

**STOP and wait for user to answer questions and confirm understanding before proceeding.**

### Step 2: Plan
Create a step-by-step implementation plan. Number each step. For each step specify:
- **File**: full path to create or modify
- **What**: specifically what to add or change (name the functions, types, components, routes — not vague descriptions)
- **How it connects**: what it imports from or exports to other files
- **Verify**: how to confirm this step works before moving to the next

Flag:
- What could go wrong? What's the riskiest part?
- Will this change survive a weekly sync? (lot IDs regenerate every sync — use lot numbers as stable keys)
- Does this touch the client/server boundary? (`better-sqlite3` cannot be imported client-side)
- **Patterns to follow** — conventions established by prior batches that this batch must match (naming, error handling, response format, component structure)
- **External dependencies** — anything requiring services and how to handle during development

### Step 3: Requirements

Convert the plan into a requirements checklist. Merge the batch document's acceptance criteria with any additional requirements discovered during planning. Each item must be:
- Specific (not vague)
- Testable (yes/no verifiable)
- Grouped by: **Functional**, **Error Handling**, **Edge Cases**, **Tests**

Every batch must include:
- Basic loading states for any UI that fetches data
- Error states for any UI that can fail (API errors, empty states)
- Input validation on any user-facing forms or API endpoints

Include test scenarios:
- **Happy path**: standard successful flow
- **Error case**: invalid input, auth failures, API errors
- **Edge case**: empty data, boundary values, concurrent access

Save to `docs/batches/{batch-id}-requirements.md`

**STOP and wait for user approval before implementing.**

After approval:
1. Create the feature branch — `git checkout -b batch/{batch-id}`
2. Update `CLAUDE.md` batch queue: set this batch's status from `ready` to `in-progress`

## Rules
- If anything in the batch document contradicts `Architecture.md` or `CLAUDE.md`, flag it and ask — do not assume
- Include test scenarios in the requirements (happy path, error case, edge case)
- Never propose changes to `data/inventory.json` — only `npm run sync` writes that file
- Never propose destructive DB operations — use migrations in `lib/db.ts migrate()` for schema changes
- Check whether the batch's data model survives the weekly sync (drop + re-insert of inventory tables)
- If LESSONS.md contains relevant warnings or patterns, call them out explicitly
- Do not start writing code — this skill only produces the plan and requirements
- Use conventional commits: `feat:`, `fix:`, `docs:`, `test:`, `refactor:`
