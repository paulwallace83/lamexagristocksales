# /refactor — Address Review Findings

## Description
Run after all review agents have saved their findings. Reads all review files for the current batch and systematically addresses every finding.

## Instructions

Read all review files for this batch:
- `docs/reviews/{batch-id}-retro.md`
- `docs/reviews/{batch-id}-correctness.md`
- `docs/reviews/{batch-id}-security.md`
- `docs/reviews/{batch-id}-integration.md`

For each finding, take action based on severity:

### Critical (must fix before merge)
- Make the fix immediately
- Show before/after for each change
- If you CANNOT fix it, explain exactly why and add an entry to `LESSONS.md`

### Important (should fix)
- Fix it if straightforward
- If deferring, add a TODO comment in the code with the full finding text
- Add a note to `docs/reviews/{batch-id}-deferred.md`

### Minor (nice to have)
- Fix if trivial
- Otherwise add a TODO comment in the code with the finding text

## After All Changes
1. Re-read each review file
2. Confirm every finding was addressed (fixed, TODO'd, or documented)
3. List any findings NOT addressed and explain why
4. For any finding you could not fix, add an entry to `LESSONS.md` explaining why and what the workaround is
5. Run `npm test` — all tests must pass
6. Run `npx tsc --noEmit` — must be clean

## Rules
- Do NOT skip any findings
- Do NOT claim something is "fine as-is" without a specific technical justification
- If a reviewer was wrong, explain specifically why — don't just dismiss it
- Run the test suite after all changes to verify nothing broke
- Never introduce unrelated changes while fixing review findings
- If a security finding involves path traversal or data privacy, it is automatically Critical regardless of how the reviewer classified it
