# /refactor — Address Review Findings

## Description
Run after all review agents have saved their findings. Reads all review files for the current batch and systematically addresses every finding.

## Instructions

### Step 1: Gather context

1. `/CLAUDE.md` — project rules and conventions
2. `/docs/Architecture.md` — system design, data model, role permissions
3. `/LESSONS.md` (if it exists) — accumulated project knowledge
4. The Batch ID - `docs/batches/{batch-id}`
5. The requirements file: `/docs/batches/{BATCH-ID}-requirements.md` (if it exists)

### Step 2: Read all review files

Read all review files for this batch:
- `docs/reviews/{batch-id}-retro.md` - self-assessment from the implementing agent
- `docs/reviews/{batch-id}-correctness.md` - bug findings
- `docs/reviews/{batch-id}-security.md` - security findings
- `docs/reviews/{batch-id}-integration.md` — pattern consistency and future batch readiness

Build a consolidated list of ALL findings across all four reviews. Note where multiple reviewers flagged the same issue — those are high-confidence problems.

### Step 3: Triage

For each finding, classify it:
- **Fix** — will address now
- **Defer** — valid finding but out of scope for this batch
- **Disagree** — the reviewer was wrong (must justify with specific technical reasoning)

Present the full triage list to the user before making any changes. Format:

| # | Source | Severity | File | Finding | Action |
|---|--------|----------|------|---------|--------|
| 1 | correctness | Critical | lib/auth.ts:42 | ... | Fix |
| 2 | security | Important | app/api/contracts/route.ts:18 | ... | Defer |
| 3 | integration | Minor | components/status-badge.tsx | ... | Disagree — [reason] |

**STOP and wait for user approval of the triage before proceeding.**

### Step 4: Fix Critical findings
Address every Critical finding immediately. For each fix:
1. Read the file and the specific lines referenced
2. Make the change
3. Verify the fix doesn't break other code (`npm run build`, run tests)
- If you CANNOT fix it, explain exactly why and add an entry to `LESSONS.md`

### Step 5: Fix Important findings
- Fix it if straightforward
- If deferring, add a TODO comment in the code with the full finding text
- Add a note to `docs/reviews/{batch-id}-deferred.md`

### Step 6: Handle Minor findings

For Minor findings:
- If it's a one-line fix, just fix it
- Otherwise, add a TODO comment in the code with the finding text

### Step 7: Record deferred items

If any Important or Minor findings were deferred, create or update `docs/reviews/{batch-id}-deferred.md`:

# Deferred Findings — Batch {BATCH-ID}

| # | Source | Severity | File | Finding | Reason Deferred | Target Batch | Status |
|---|--------|----------|------|---------|----------------|-------------|--------|
| 1 | security | Important | ... | ... | ... | Next batch / TBD | OPEN |

### Step 8: Update docs if flagged

If the integration review flagged doc updates needed:
- Update `/CLAUDE.md` if the project description, sprint context, or key files section is out of date
- Update `/docs/Architecture.md` if the implementation diverged from the documented design
- Update `/LESSONS.md` with any lessons from findings that couldn't be fixed or required workarounds

### Step 9: Final verification

1. Run `npm run build` — must pass
2. Run tests (`npm test` or equivalent) — must pass
3. Re-read each review file and confirm every finding was addressed:
   - Fixed (reference the change)
   - Deferred (reference the TODO comment and deferred.md entry)
   - Disagreed (reference the justification)
4. Run `git diff --stat` to summarise all changes made
5. 6. Run `npx tsc --noEmit` — must be clean
6. For any finding you could not fix, add an entry to `LESSONS.md` explaining why and what the workaround is

Present a final summary:

```
## Refactor Summary — Batch {BATCH-ID}

### Fixed: X findings
- [list each with file and one-line description]

### Deferred: X findings
- [list each with reason]

### Disagreed: X findings
- [list each with justification]

### Build: PASS / FAIL
### Tests: PASS / FAIL
```

## Rules

- Do NOT skip any findings — every single finding must be addressed (fixed, deferred with TODO, or disagreed with justification)
- Do NOT claim something is "fine as-is" without a specific technical justification referencing the code
- If a reviewer was wrong, explain specifically why — cite the line of code that proves it. "I think it's fine" is not a justification.
- Do NOT make changes beyond what the reviews flagged — this is a refactor pass, not a feature pass
- If a fix introduces a new pattern inconsistency (flagged by integration review), follow the existing pattern, not your preferred pattern
- If you cannot fix a Critical finding, explain exactly why and add an entry to `/LESSONS.md`
- Always get user approval on the triage before making changes
- Use conventional commits when done: `fix: address batch {BATCH-ID} review findings`
