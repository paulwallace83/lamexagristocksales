# /retro — Post-Implementation Retrospective

## Description
Run immediately after implementation is complete, BEFORE compacting context. This captures the implementing agent's honest self-assessment while it still has full memory of every decision and shortcut.

## Instructions
Review all code you created or modified in this batch. For each file:

1. **Confidence Rating (1-10)** — how confident are you this code is correct?
2. **Uncertainty** — what are you NOT fully confident about?
3. **Refactoring** — what would improve quality if you had more time?
4. **Shortcuts** — what corners did you cut?
5. **Edge Cases** — what scenarios did you not handle?

Be brutally honest. It is better to catch issues now than in review.

### Lamex-Specific Checks
For each file also consider:
- **Sync survival:** Does any new data use lot IDs instead of lot numbers? Will it survive a weekly sync?
- **Data privacy:** Could any output leak customer names, pricing, or sensitive ERP fields?
- **Client/server boundary:** Is `better-sqlite3` safely on the server side only?
- **Path safety:** Are all user-derived path segments sanitised + resolved + prefix-checked?

### Cross-cutting concerns

Check these across the entire batch:
- **Error handling** — do all API routes return appropriate status codes? Are errors logged server-side? Are stack traces hidden from clients?
- **Loading & empty states** — does every UI component that fetches data handle loading and empty/zero-result states?
- **Auth & roles** — are all new routes protected? Do role restrictions match the permissions table in Architecture.md?
- **Audit logging** — are auditable actions (from Architecture.md AuditLog section) actually logged?
- **Validation** — is every user input validated with Zod before processing?
- **TypeScript** — any `any` types, missing return types, or suppressed errors?

### Check against project standards

1. Read `/CLAUDE.md` — did the batch follow all development rules?
2. Read `/LESSONS.md` (if it exists) — did the batch avoid known pitfalls?
3. Read `/docs/reviews/` (if prior retros exist) — did the batch repeat any previously flagged issues?

## Output
Save findings to `docs/reviews/{batch-id}-retro.md` using this format:

```markdown
# Retrospective — {Batch ID}

## Summary
(2-3 sentence overall assessment)

## Acceptance Criteria Status
| # | Criterion | Status | Notes |
|---|-----------|--------|-------|
| 1 | ... | PASS / PARTIAL / MISS | ... |

## File-by-File Review

### {filename}
- **Confidence:** X/10
- **Uncertainties:** ...
- **Suggested Refactoring:** ...
- **Shortcuts Taken:** ...
- **Unhandled Edge Cases:** ...

## Cross-Cutting Concerns
- **Error handling:** ...
- **Loading & empty states:** ...
- **Auth & roles:** ...
- **Audit logging:** ...
- **Validation:** ...
- **TypeScript:** ...

## Items Needing Immediate Attention
(Anything rated below 7, any PARTIAL/MISS criteria, any security issues. Each item should state the file, the problem, and what the fix is.)

## Items for Future Batches
(Things that aren't urgent but should be tracked — tech debt, deferred improvements, known limitations.)

## Lessons Learned
(Anything surprising, painful, or worth remembering for the next batch. These will be appended to /LESSONS.md.)
```
After saving the retro, append any entries from "Lessons Learned" to `/LESSONS.md` (create the file if it doesn't exist).

## Rules
- Do NOT compact context before running this
- Do NOT skip files — review every file touched
- Anything rated below 7 must be flagged for immediate fixing
- Any PARTIAL or MISS acceptance criteria must appear in "Items Needing Immediate Attention"
- Be specific — "could be better" is not useful, "the error handler on line 42 swallows the original error message" is useful
- Always check for data privacy violations — customer names and pricing are the highest-severity leak in this project
- Reference line numbers and function names, not vague descriptions
- If you find a security issue, flag it regardless of confidence rating
