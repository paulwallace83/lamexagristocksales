## Critical (must fix before merge)

- **`lib/sync-apply.ts` (lines 195-304) — Missing lot and lot_contract insertion in the seed transaction.** The seed transaction deletes `lots` and `lot_contracts` (lines 200-201) but never re-inserts them, despite `inventory.json` containing `listings[].lots[]` arrays with lot-level data (lot numbers, quantities, weights, BBDs, contracts). Compare with `lib/db.ts autoSeed()` (lines 316-341) which inserts lots via `insertLot`, handles duplicate lot numbers within a listing via `findLot`/`updateLot`, and inserts lot-contract associations via `insertLotContract`. The `autoSeed()` function only runs when the `products` table is empty (line 258-261 of `lib/db.ts`), and since `applySync()` re-inserts products in its transaction, `autoSeed()` will never fire after a sync. This means after every weekly sync: (a) `relinkDocumentLots()` finds zero lots, returning `{ linked: 0, orphaned: N }` for all documents; (b) `relinkCoaData()` finds zero lots, orphaning all saved COA data; (c) `deductDiscountLots()` finds zero lots, marking all active discount items as "missing". This is a pre-existing bug carried over from the original `scripts/sync-inventory.ts` on `main`, but since B004's purpose is to extract the sync pipeline into a reusable library function, it should be fixed here. Impact on future: B006 (`apply_sync` agent tool) and B007 (`--dry-run`) both depend on `applySync()` producing a correct database state.

- **`tests/sync-apply.test.ts` + `lib/sync-apply.ts` (lines 416-475) — Running tests corrupts tracked reference files.** The happy-path test (line 203) calls `applySync()`, which invokes `regenerateSuppliersMd()` and `regenerateWarehousesMd()`. These functions write to `process.cwd()` — the project root during test execution — using the minimal test fixtures (1 supplier "Supplier A", 1 warehouse "Cold Storage LA"). This overwrites the real `suppliers.md` (17 suppliers) and `warehouses.md` (9 warehouses) with test data. The git diff for this batch confirms the damage. This conflicts with the existing test pattern: `tests/documents.test.ts` mocks `getUploadsRoot`, `tests/coa-data.test.ts` mocks `getDb`, and `tests/agent-sync-tools.test.ts` mocks all transitive dependencies — none of them write to the project root. Fix options: (a) make the reference file generators accept an output directory parameter and pass the temp dir in tests, or (b) mock `writeFileSync` at the module level in the test file. Impact on future: every CI run and local test run will corrupt these files; if committed, the production reference data is lost.

## Important (should fix, can be next batch)

- **`lib/sync-apply.ts` `readJson()` (lines 91-98) — Error message conflates missing file with malformed JSON.** The helper wraps both `readFileSync` and `JSON.parse` in a single try-catch, producing "Failed to parse JSON: {path}" even when the file simply doesn't exist (ENOENT). The existing `lib/sync.ts safeReadJson<T>()` (lines 230-244) separates these into two distinct try-catch blocks with different messages: "Cannot read {label}" for missing files and "Invalid JSON in {label}" for parse errors. This matters operationally — seeing "Failed to parse JSON: suppliers.json" when the file is missing sends the operator down the wrong troubleshooting path. Should either export and reuse `safeReadJson` from `lib/sync.ts` or replicate the two-stage error pattern.

- **`lib/sync-apply.ts` `regenerateSuppliersMd()` / `regenerateWarehousesMd()` (lines 445, 474) — Hardcoded `process.cwd()` output path.** For the CLI wrapper this works correctly. For B006 (route handler calling `applySync()`), `process.cwd()` on Railway resolves to `/app`, which is also correct. However, a library function should not implicitly depend on `process.cwd()` for output paths. Consider accepting an optional `rootDir` parameter (defaulting to `process.cwd()`) to make the dependency explicit and testable. This also directly enables the test corruption fix from Critical #2.

- **`tests/sync-apply.test.ts` — Thin coverage relative to the function's complexity.** Only 4 tests: missing proposed file, concurrent lock, lock cleanup on error, and happy path. Missing coverage for: (a) malformed JSON input (e.g., `suppliers.json` containing invalid JSON); (b) `products` array missing from proposed JSON; (c) snapshot sequential naming (multiple syncs per day); (d) new arrivals detection path (snapshot has different products than proposed); (e) discount validation path (`validationReport !== null` when active discount items exist). Compare with `tests/sync-validation.test.ts` (21 tests) and `tests/coa-data.test.ts` (23 tests) which cover edge cases thoroughly. The B004 requirements checklist specifies 4 test scenarios which are all covered, but the function has ~15 distinct behavioral paths. Since B006 and B007 depend on this function, insufficient coverage here cascades downstream.

- **`tests/sync-apply.test.ts` (lines 40-45) — Temp directories in `/tmp` are never cleaned up.** `makeTmpDir()` creates unique directories under `/tmp` but neither `afterEach` nor `afterAll` removes them. Only the lock file is cleaned up in `afterEach`. While harmless on CI (ephemeral containers), local development will accumulate test detritus. The existing pattern in `tests/documents.test.ts` avoids filesystem side effects entirely by mocking `fs` operations.

## Minor (nice to have)

- **`lib/sync-apply.ts` `readJson()` (line 91) — Returns `any` with no type narrowing.** The existing `lib/sync.ts safeReadJson<T>()` is generic and returns a typed result. The `any` return cascades through `applySync()`, requiring inline `(p: any)` type assertions in several places (e.g., lines 346, 375). Using at minimum `{ products?: unknown[] }` as a return type constraint would catch structural errors earlier and align with the LESSONS.md pattern of guarding against runtime type mismatches from JSON sources.

- **`lib/sync-apply.ts` (line 72-78) — File lock uses check-then-write (TOCTOU race).** `acquireLock()` calls `existsSync()` then `writeFileSync()`. Two concurrent invocations could both pass the existence check and both write the lock. Using `writeFileSync(lp, data, { flag: 'wx' })` (exclusive create, atomic on POSIX) would eliminate the race. For a single-user internal tool on a single-node Railway deployment this is low risk, but the atomic pattern is equally simple.

- **`scripts/sync-inventory.ts` (lines 10-13) — Misleading log ordering.** The output prints "Preflight: validating JSON files..." and "All JSON files valid" after `applySync()` has already completed (preflight ran inside `applySync()`). This gives the terminal user the impression the preflight just happened, when in fact all sync steps are already done. The cosmetic fix is to either remove these lines or print them before calling `applySync()`.

- **`scripts/sync-inventory.ts` (lines 117-119) — Discount validation active count is reconstructed indirectly.** The active count is computed as `vr.validated + vr.missing + vr.overlaps.length` rather than using a direct count from `getDiscountItems("active")`. The original script used `activeDiscountItems.length` directly. While mathematically equivalent when `validateDiscountItems` processes all active items, the indirect computation is fragile if the validation function's semantics change.

- **`lib/sync-apply.ts` (line 47) — `OrphanedDoc` type is exported but only used internally.** It is implicitly available through `SyncApplyResult.orphanedDocs`, so the separate export adds public surface area without utility. Not harmful, but inconsistent with other internal types in the file which are not exported.
